# Qryx 1.2.0

This is a minor release. It adds a subcommand, `qryx ssh`, and a key exchange finding to `qryx tls`, and it rebuilds the `qryx` binaries and the image, `ghcr.io/taipanbox/qryx`, on Go 1.27.4, which fixes GO-2026-6859 in `net/http`. The 1.1.1 release was built on Go 1.27.3. No name `compat/1.0.json` freezes is removed or renamed; the additions are listed under `additive` there.

## New

- **`qryx ssh host:port` reads what an SSH server offers (#87).** It sends an identification string and reads the server's identification and `SSH_MSG_KEXINIT`, the algorithm lists a server sends in the clear before any key exchange or authentication. qryx never sends a KEXINIT of its own, so nothing is negotiated and nobody logs in. It reports the banner as the SSH protocol asset, a key exchange verdict (no risk when `mlkem*` or `sntrup*` is offered, quantum-vulnerable when it is not), each broken algorithm still offered once however many directions offer it, and one finding per host key family, graded like every other key. Every length the server sends is checked before it is used. Like `qryx tls`, it connects only to the exact `host:port` arguments given, with `--timeout` as the connect timeout.
- **`qryx tls` reports the key exchange group (#87).** The group the session key was agreed with is named from its IANA code point. qryx offers the hybrid `X25519MLKEM768` first, so a server that takes it is reported with it and no risk, and a server that agrees `X25519` or a NIST curve alone is reported as quantum-vulnerable, severity high.
- **Reports know the new source (#87).** The new source `ssh-probe` has an agility row (medium), the NCSC coverage report has a seventh bucket, `ssh`, a finding seen through a live SSH probe counts as externally facing, and the CBOM calls a hybrid exchange `kem` rather than `key-agree`.

## Upgrade

A scan that gates on live TLS findings can fail where it passed before. A server that agrees a classical group alone now produces a high-severity quantum-vulnerable finding, so a step that runs `qryx tls ... --fail-on high` (or `--fail-on-new` against an older baseline) reports it. That is the intended result of the new finding, and nothing else about the exit status changes. Check the gate's baseline before upgrading a CI step that probes live endpoints.

Pull `ghcr.io/taipanbox/qryx:v1.2.0` in place of `v1.1.1`, or download the binary for your platform from this release. No setting, stored state or wire format changes, and no existing flag changes meaning, so there is nothing to migrate. To roll back, run 1.1.1 again.
